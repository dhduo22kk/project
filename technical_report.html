§1시스템 개요 및 문제 정의

기존 보험 TM 채널의 상품 추천 시스템은 AutoGluon 기반 테이블 학습 모델로 고객별 상품 가입 확률을 산출하고, 상위 \(k\)개 상품명과 고정 텍스트를 출력하는 구조다. 이 방식의 구조적 한계는 세 가지다.

  • 근거 부재: 추천 점수의 생성 근거(담보 공백, 과거 발화, 유사 고객 패턴)가 출력에 포함되지 않아 상담사가 실제 통화에서 활용하기 어렵다.
  • 맥락 단절: 통화 녹취 5천 건이 비정형 WAV로만 보관되어 어떤 파이프라인에도 연결되지 않았다.
  • 단편 출력: "상품명 + 고정 안내 문구" 형태로, 고객별 맞춤 스크립트 각도(담보 보완 / 설계 팔로업 / 신상품 공략)를 선택하는 논리가 없다.

본 시스템은 이 세 한계를 각각 LLM 생성 근거 설명, STT 기반 RAG 인덱싱, 스크립트 각도 3분기 자동 결정으로 대응한다. AutoGluon 배치는 그대로 유지하되, 그 출력(\(\hat{p}_{\text{ML}}\), 상품 순위)을 RAG 컨텍스트 및 담보 GAP 분석과 함께 LLM에 주입하는 방식으로 연동한다.

§3RAG 검색 설계

3.1 임베딩 및 유사도 함수

RAG 검색의 핵심은 쿼리 벡터와 인덱스 내 문서 벡터 간의 유사도 측정이다. 본 시스템은 nomic-embed-text(Ollama 서빙, 출력 차원 \(d = 768\))를 사용하며, Chroma 내부 검색은 코사인 유사도를 기본 지표로 한다.

(1) \[ \text{sim}(\mathbf{q}, \mathbf{d}) \;=\; \frac{\mathbf{q} \cdot \mathbf{d}}{\|\mathbf{q}\|\,\|\mathbf{d}\|} \;=\; \frac{\displaystyle\sum_{i=1}^{d} q_i d_i}{\displaystyle\sqrt{\sum_{i=1}^{d} q_i^2}\;\sqrt{\sum_{i=1}^{d} d_i^2}} \]
q: 쿼리 임베딩 벡터 ∈ ℝ768  |  d: 인덱스 문서 임베딩 ∈ ℝ768  |  값역: [−1, 1] (정규화 후 [0, 1])

top-\(k\) 검색은 인덱스 \(\mathcal{D} = \{d_1, \ldots, d_N\}\)에 대해:

(2) \[ \mathcal{R}_k(\mathbf{q}) \;=\; \underset{S \subseteq \mathcal{D},\, |S|=k}{\arg\max} \sum_{\mathbf{d} \in S} \text{sim}(\mathbf{q}, \mathbf{d}) \]

Chroma는 HNSW(Hierarchical Navigable Small World) 인덱스를 사용하며 근사 최근접 이웃(ANN) 검색을 수행하므로, 이론적 정확 최근접 이웃과 달리 실제 결과는 recall이 보장된 근사값이다.

3.2 케이스별 RAG 전략

고객 분류(신규 / 미연결 / 이력)에 따라 RAG 쿼리 방식이 달라진다.

고객 유형검색 방식쿼리 텍스트 구성k
이력 고객 collection.get(where={"CTMNO": ctmno}) 직접 조회 (유사도 검색 없음) —
신규 고객 collection.query(query_texts=[…]) "[고객: {age}세 {sex}, {campaign}] {담보 gap 요약}" 5
미연결 고객 collection.query(query_texts=[…]) 인구통계 + 담보 gap (캠페인 필터 제거) 5

Chroma calls 컬렉션의 임베딩 대상 텍스트(embedded_text) 포맷은 아래와 같이 고정한다:

f"[고객: {CTM_AGE}세 {CTM_SEX}, {CAMPAIGN_NM}] {summary}"

이 구성은 쿼리 텍스트와 동일한 시맨틱 공간에 위치하도록 설계되어, 인구통계 + 캠페인 컨텍스트를 함께 고려한 유사도 계산이 가능하다. 캠페인명이 없는 경우 "캠페인미확인"으로 대체하여 null 값이 임베딩에 영향을 주지 않도록 한다.

3.3 메타데이터 필터

Chroma 메타데이터 필터 조건은 스칼라 타입(string / int / float / bool)만 지원한다. 따라서 keywords 리스트는 comma-separated string으로 저장하며, 채널·캠페인명 기반 pre-filter 후 유사도 재정렬(post-filter)을 적용한다.

설계 결정: products RAG의 chunk 단위는 "페이지/슬라이드 1개 = 1 document". 평균 500~800 토큰 범위로, 하나의 문서가 지나치게 세분화되어 문맥이 잘리는 over-chunking을 방지한다.

§4VRAM 및 모델 자원 분석

4.1 LLM 모델 메모리 추정

GGUF Q4_K_M 양자화에서 파라미터당 실효 비트 수는 약 4.5 bits다. Qwen3.6-27B의 VRAM 점유량은:

(3) \[ M_{\text{model}} \;=\; \frac{N_{\text{param}} \times b_{\text{quant}}}{8 \times 1024^3} \;\text{[GiB]} \]
N_param = 27 × 109  |  b_quant = 4.5 bits (Q4_K_M 실효값)  |  ∴ Mmodel ≈ 15.2 GiB

4.2 KV 캐시 메모리

KV 캐시는 Transformer 각 레이어의 Key·Value 행렬을 저장한다. Qwen3.6 계열의 레이어 수 \(L = 64\), 헤드 수 \(H = 64\), 헤드 차원 \(D_{\text{head}} = 128\) 기준:

(4) \[ M_{\text{KV}} \;=\; 2 \times L \times H \times D_{\text{head}} \times T_{\text{ctx}} \times \frac{b_{\text{kv}}}{8 \times 1024^3} \;\text{[GiB]} \]
인수 2: Key + Value  |  T_ctx = 컨텍스트 토큰 수  |  b_kv = 16 bits (FP16)  |  Tctx = 8,192 토큰 시 MKV ≈ 17.2 GiB

전체 VRAM 예산은 아래 표와 같다.

4.3 Pipeline A 자원 충돌 회피

STT 인덱싱 중 Whisper(3.1 GiB) + Qwen3.6(15.2 GiB) + nomic(1.0 GiB)가 동시에 VRAM을 점유하면 합계 19.3 GiB로 단독 실행 시 문제가 없다. 그러나 Gradio 서비스가 동시에 실행 중이라면 KV 캐시까지 포함한 총량이 40 GiB를 초과할 수 있으므로, Pipeline A는 서비스 가동 전 1회성으로 완료하는 것을 설계 원칙으로 정한다.

§5배치 파이프라인 처리 시간 모델

5.1 Pipeline A 총 소요 시간

녹취 1건 처리 시간은 STT, LLM 분석, 임베딩 세 단계의 합이다.

(5) \[ t_{\text{item}} \;=\; t_{\text{STT}} + t_{\text{LLM}} + t_{\text{embed}} \]

각 단계의 실측 범위와 전체 5천 건 예상 소요 시간:

(6) \[ T_{\text{total}} \;=\; N \times \mathbb{E}[t_{\text{item}}] \;=\; 5{,}000 \times \bigl(\,\overline{t}_{\text{STT}} + \overline{t}_{\text{LLM}} + \overline{t}_{\text{embed}}\,\bigr) \]

5.2 Resume 로직의 기대 절감 효과

중간 장애 발생 시 resume 없이 전체 재처리하는 비용은 \(T_{\text{total}}\)이지만, CALL_ID 단위 skip 체크 시 기대 추가 처리 시간은 장애 시점 이후 건수만큼으로 감소한다. \(f\)를 장애 발생 진행률, \(c_{\text{skip}}\)을 건당 skip 확인 비용(< 0.01 s)이라 하면:

(7) \[ \Delta T_{\text{resume}} \;=\; (1 - f) \cdot N \cdot \mathbb{E}[t_{\text{item}}] \;+\; N \cdot c_{\text{skip}} \;\ll\; T_{\text{total}} \]

중간 장애 후 재시작 시 기존 처리분은 Chroma에서 collection.get(ids=[call_id])로 확인하여 skip하므로, 추가 비용은 이미 처리된 건의 skip 체크 합계 \(f \cdot N \cdot c_{\text{skip}}\)뿐이다.

§6캠페인 성과 추정 방법론

6.1 체결률 점추정

Tab2에서 "직전 캠페인 성과 참고치"로 표시하는 값은 ML 예측이 아닌, 동일 캠페인의 과거 체결 데이터에서 산출한 빈도주의 점추정이다. 배정일 기준 \(\tau = 90\)일 이내 계약 체결을 성공으로 정의하면:

(8) \[ \hat{p} \;=\; \frac{K}{N} \]
K: 90일 이내 체결 건수  |  N: 해당 캠페인 총 배정 건수

6.2 Wilson 신뢰구간

표본이 충분히 크지 않을 경우 정규근사 기반 신뢰구간은 과대·과소 추정을 유발한다. 이를 보정하는 Wilson Score Interval은 다음과 같다.

(9) \[ \text{CI}_{1-\alpha} \;=\; \frac{1}{1 + \tfrac{z^2}{N}} \left( \hat{p} + \frac{z^2}{2N} \;\pm\; z\sqrt{\frac{\hat{p}(1-\hat{p})}{N} + \frac{z^2}{4N^2}} \right) \]
z: 표준 정규분위수 (95% 신뢰구간: z = 1.96)  |  N: 배정 총 건수  |  α = 0.05

예시: 과거 캠페인 배정 3,000건, 체결 500건인 경우 \(\hat{p} = 0.167\), Wilson 95% CI ≈ (0.153, 0.181). UI에는 "예상 체결 약 460 ~ 543건 (95% CI)" 형태로 표시하며, "ML 예측 아님, 과거 실적 참고치"임을 명시한다.

6.3 목표 인원 수 달성 기대 추출 효율

목표 \(M\)명 추출 시 기대 체결 건수:

(10) \[ \mathbb{E}[\text{체결}] \;=\; M \cdot \hat{p} \quad,\quad \text{SD} \;=\; \sqrt{M \cdot \hat{p}(1 - \hat{p})} \]

§8데이터 설계 및 ETL

8.1 DuckDB 도메인 테이블 구성

Oracle OLTP 원본에서 DuckDB 분석 스냅샷으로의 ETL은 두 단계로 진행된다.

  1. oracle_queries.sql (Oracle 실행): 복잡한 JOIN·CASE WHEN 로직을 처리하여 AI_* 추출 뷰/테이블 생성
  2. pipeline_c_duckdb.py (Python 실행): SELECT * FROM AI_* 쿼리로 pandas DataFrame 수신 후 DuckDB에 적재

이 분리로 Oracle 쪽 복잡도가 Python 코드에 유입되지 않으며, 쿼리 변경 시 SQL 파일만 수정하면 된다.

8.2 통화 결과 코드 ETL 변환

Oracle 원본 코드를 그대로 적재하지 않고, ETL 시점에 사람이 읽을 수 있는 레이블로 번역하여 LLM 프롬프트 주입 시 추가 디코딩이 불필요하다.

-- oracle_queries.sql 내 CASE WHEN 예시
CASE
  WHEN CONTACTMINORCD IN ('020206','030202') THEN '결번'
  WHEN DIALRESULTCD = '02'                  THEN '타인통화'
  WHEN tc.CALLID IS NULL                    THEN '미연결'
  ELSE '연결성공'
END AS RESULT_CD

8.3 DuckDB 무중단 갱신 (Atomic Rename)

매일 cron 실행 시 진행 중인 에이전트 쿼리와의 충돌을 방지하기 위해 별도 파일에 먼저 쓰고 교체하는 방식을 채택한다.

# pipeline_c_duckdb.py
conn_new = duckdb.connect(DUCKDB_NEW_PATH)   # 별도 파일에 적재
# ... TRUNCATE + INSERT ALL TABLES ...
conn_new.close()
os.replace(DUCKDB_NEW_PATH, DUCKDB_PATH)     # atomic rename — POSIX 보장

os.replace()는 POSIX 파일시스템에서 원자적 연산이므로, 에이전트가 mart.db를 읽는 도중에 교체가 발생해도 파일 핸들이 유지되어 데이터 손상이 없다.

§9보안 및 개인정보 처리

9.1 2단계 개인정보 마스킹

녹취 STT 텍스트는 즉시 2단계 마스킹을 거친다. 원문은 어디에도 저장되지 않으며, 마스킹된 텍스트만 Chroma metadata에 보관된다.

단계처리대상 패턴
1단계 (Regex) Python 정규식 전화번호, 주민번호, 계좌번호, 카드번호
2단계 (LLM) Qwen3.6 JSON 출력 이름, 주소 등 비정형 식별 정보

2단계는 1단계 처리 완료 텍스트를 입력으로 받으며, 마스킹 + 분석(감성/키워드/요약)을 단일 LLM 호출로 처리하여 호출 횟수를 최소화한다.

9.2 폐쇄망 보안 아키텍처

  • 모든 LLM 추론은 사내 GPU 서버 로컬에서 Ollama가 처리 — 외부 API 호출 없음
  • LangChain Hub, LangSmith 의존성 완전 제거 (HTTP 통신 불가 환경)
  • Gradio server_name="0.0.0.0"으로 사내망 IP 접근 허용, 네트워크 레벨 통제는 정보보호 파트 담당
  • 컴플라이언스 승인 완료 컬럼만 DuckDB 적재 (청구/보상 이력 등 민감 데이터 제외)

§10한계 및 향후 방향

10.1 현재 한계

  • Pipeline A 소요 시간: 5천 건 처리에 35~78시간 소요로, 서비스 가동 전 완료해야 한다. Whisper 배치 병렬화나 vLLM 다중 프로세스로 단축 가능하나 MVP 범위 외.
  • LLM 평가 부재: Qwen3.6이 생성한 스크립트의 품질을 정량 지표(ROUGE, LLM-as-judge)로 자동 평가하는 파이프라인이 없어 운영 품질 모니터링이 수동 의존적이다.
  • DuckDB 단일 쓰기 제약: DuckDB는 단일 writer 모델로, Pipeline C 실행 중 mart_new.db에 대한 동시 쓰기는 불가능하다. 현재 구조(cron 단독 실행)에서는 문제 없으나 향후 수동 갱신 버튼과의 충돌 방지 로직이 필요하다.
  • tbl_coverage_detail, tbl_cvr_group_map 이월: 담보코드 단위 LIKE 검색 및 커스텀 그룹 매핑은 MVP 이후 구현 예정.

10.2 향후 확장 방향

  • 레거시 UI 연동: Gradio API를 통해 기존 이노스 상담사 화면에 AI 추천 결과를 주입하는 방식으로 UI 교체 없이 연동 가능.
  • SFP 채널 확장: 현재 TM/CM 채널 설계이나, CHANNEL_TYPE 메타데이터와 라우터 로직의 채널 분기를 추가하면 SFP 채널로 확장 가능.
  • tbl_change_log: 계약 체결/문자 발송/통화 진행 등 임팩트 있는 이벤트를 감지하여 고객 상태 변화를 추적하는 로그 테이블. M4에서 구현 예정.
  • 비전 LLM 활성화: 상품 설명서 이미지 슬라이드를 마크다운으로 변환하는 비전 LLM 파이프라인이 구현되어 있으나, 모델 미정으로 실제 호출이 비활성화 상태.
