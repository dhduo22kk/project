§1기여 포지셔닝

기존 시스템은 상품명을 예측한다. 이 에이전트는 고객 맥락을 파악하여 왜 이 상품인지, 어떻게 말할지를 생성한다.

TM 채널의 기존 상품추천 시스템은 고객의 계약 이력과 인구통계를 기반으로 AutoGluon이 가입 확률을 예측하고, 상위 상품명과 고정 비교 문구를 출력한다. 상담사 화면에 노출되지만, 통화 맥락이 없는 상품명만으로는 실제 대화에서 활용되기 어렵다.

RAG 설계 — 이력/신규 이중 전략

이력 고객 — 직접 조회

collection.get(where={"CTMNO": ctmno})

유사도 검색 없이 해당 고객의 과거 통화 요약을 그대로 가져온다. 다른 고객 녹취가 섞이지 않아 "3월에 말씀하셨던 허리 수술 걱정" 같은 고객 특이 맥락을 정확히 재활용할 수 있다.

신규·미연결 — 유사도 검색

collection.query(query_texts=["[고객: {나이}세 {성별}, {캠페인명}] {담보gap}"])

임베딩 텍스트를 저장 시와 동일한 형식으로 구성하여 같은 시맨틱 공간에서 검색한다. 유사 인구통계의 성공 통화 top-3를 참조해 첫 접촉 스크립트를 구성한다.

nomic-embed-text 임베딩 설계

Ollama 내 nomic-embed-text(768dim)로 단일화하여 별도 임베딩 서버가 필요 없다. 임베딩 대상 텍스트 형식을 고정한다:

임베딩 텍스트 포맷 (저장 시 / 검색 쿼리 시 동일)
[고객: {나이}세 {성별}, {캠페인명}] {통화 요약 텍스트}

저장 시와 검색 쿼리 시 동일한 형식을 사용하여 시맨틱 공간의 불일치를 방지한다. 캠페인명이 없는 경우 "캠페인미확인"으로 대체한다.

§4캠페인 추천 대상 추출 플로우

Tab1의 고객 맥락 데이터가 Tab2 캠페인 추출의 기반이 된다. LLM이 SQL을 생성하지 않는다 — 구조화된 폼 응답이 검증된 쿼리 템플릿으로 변환된다.

LLM 직접 SQL 생성을 쓰지 않는 이유

LLM SQL 생성의 문제

30만 명 대상 캠페인 추출에서 SQL 오류는 잘못된 대상 발송으로 직결된다. LLM은 스키마를 정확히 모르고, 조건 누락·타입 오류 위험이 있다. 결과를 감사(audit)하기 어렵다.

조건 딕셔너리 → 템플릿 방식

UI 폼 응답 → 구조화된 conditions dict → build_campaign_query() 검증된 템플릿 함수 → DuckDB SQL. 조건이 명시적으로 수집되어 결과가 결정론적이고 감사 가능하다.

추출 전략 — 과거 실적 기반 vs 활성도 기반

전략동작 방식적용 조건
과거 실적 기반 동일 캠페인 체결 고객의 연령 분포 10~90 퍼센타일을 추출. 해당 연령 범위의 미접촉 고객 중 연락불가·중복배정 제외 후 목표 인원 무작위 추출. PERCENTILE_CONT(0.1/0.9) WITHIN GROUP (ORDER BY CTM_AGE) 동일 캠페인 체결 이력 데이터가 존재하는 경우
활성도 기반 최근 6개월 내 연결성공 통화 또는 캠페인 배정이력이 있는 고객 대상. Step 0 성별·연령·채널 조건 + 가입불가 고객 필터 적용. 신규 캠페인 포함 항상 사용 가능

추출 결과는 고객번호(CTMNO)만 포함한 Excel로 출력되어 기존 콜링·문자 발송 시스템에 그대로 업로드한다. 기존 캠페인이면 직전 실적(배정 수, 체결율)을 ML 예측이 아닌 실제 과거 실적 참고치로 함께 표시한다.

두 탭의 연결. Tab1의 tbl_call_detail(통화이력)이 Tab2 활성도 기반 추출의 핵심 소스다. 에이전트가 상담사 지원을 위해 구축하는 고객 맥락 데이터가 캠페인 타겟 효율화에도 직접 활용된다.

§5데이터 인덱싱 파이프라인

에이전트가 RAG 검색과 DB 조회에 활용하는 지식 저장소를 구축하는 오프라인 파이프라인 3개다.
파이프라인입력 → 출력핵심 처리실행
A · STT 인덱싱 WAV → Chroma calls faster-whisper 음성→텍스트 → 2단계 PII 마스킹 → Qwen3.6 JSON 분석(마스킹+감성+키워드+요약 단일 호출) → nomic-embed-text 벡터화 1회성, CALL_ID resume
B · 문서 인덱싱 PDF/PPTX/DOCX → Chroma products 포맷별 마크다운 변환(pymupdf4llm / mammoth / python-pptx) → 청크 분할 → 벡터화 1회성, 문서명 resume
C · DuckDB 갱신 Oracle → DuckDB 사전 정의 ETL 쿼리 실행 → 임시 파일 완전 적재 → POSIX atomic rename(무중단) 매일 새벽 cron
Pipeline A/B 완료 전 에이전트 동작. 개발 기간에는 Chroma 없이 DuckDB + products RAG만으로 Tab1이 작동한다. Pipeline A 완료 시 calls RAG가 자동으로 활성화된다 — 코드 변경 없음.

§6보안 및 개인정보

녹취 원문은 에이전트에 도달하지 않는다. STT 직후 마스킹 완료 후 원문 폐기, 마스킹 텍스트만 벡터 DB에 저장된다.
단계방식처리 대상
1단계 — 정규식 Python 패턴 매칭 (카드번호 우선) 전화번호, 주민번호, 계좌번호, 카드번호
2단계 — LLM Qwen3.6 JSON — 마스킹·분석 단일 호출 이름, 주소 등 비정형 식별 정보

컴플라이언스 승인 완료 컬럼만 DuckDB에 적재하며, 청구·보상 이력 등 민감 데이터는 제외한다. 모든 LLM 추론은 사내 GPU 서버에서 완결되며 외부 클라우드 API · LangSmith · LangChain Hub 등 외부 통신이 없다.
