Abstract

본 시스템은 TM 채널 전사 고객 DB(약 30만 명)와 콜센터 녹취 데이터(약 5,000건)를 통합하여, 상담사에게는 고객 맞춤 상담 스크립트를, 마케팅 기획자에게는 AI 기반 캠페인 타겟 리스트를 즉시 제공하는 멀티모달 AI Agent를 구현하였다. faster-whisper STT·Qwen3.6-27B LLM· Chroma 벡터DB·DuckDB를 결합한 HyDE 및 Dynamic Few-Shot 기법을 통해, 기존 ML 추천 시스템의 고정 스크립트 한계를 극복하고 고능률 상담사의 노하우를 전체 상담사에게 실시간으로 전달할 수 있는 지능화 파이프라인을 제시한다.

Section 1

Executive Summary

TM 채널 전사 고객 DB(약 30만 명)와 녹취 데이터를 통합하여, 상담사에게는 고객 맞춤 상담 스크립트를, 마케팅 기획자에게는 AI 기반 캠페인 타겟 리스트를 즉시 제공하는 AI Agent 시스템입니다. 기존 ML 추천 시스템이 제공하던 고정 스크립트를 넘어, 과거 성공 콜 녹취·고능률 상담사 노하우·상품 교육 자료·전사 DB를 결합한 개인화 스크립트를 생성합니다.

핵심 가치는 단순한 상품 추천 결과의 출력이 아닌, "추천 결과를 상담사가 실제로 쓸 수 있게 만드는 것"에 있습니다. 고객 맥락이 없는 추천 결과는 사실상 미사용 상태였으며, 본 시스템은 이 간극을 직접 해소합니다.

Section 2

배경 및 문제 정의

2.1 기존 시스템 구조 (AS-IS)

현재 한화손해보험 TM 채널에는 AutoGluon 기반의 ML 상품추천 배치 파이프라인이 운영 중입니다. Oracle의 M_CRM_REC_RLT_BIZ 테이블에 추천 결과(상품명, 순위)가 적재되고, gd_filter_func를 통한 자동 UW(나이·성별·보장충족 필터) 결과가 레거시 상담사 화면에 상품명과 고정 텍스트 형태로 표시됩니다.

  • AutoGluon 기반 ML 상품추천 배치 → M_CRM_REC_RLT_BIZ 적재
  • 자동 UW: gd_filter_func (나이/성별/보장충족 필터)
  • 레거시 상담사 화면: 상품명 + 고정 텍스트만 표시
  • 녹취 데이터, 통화 이력, 담보 gap 정보는 별도 시스템에 분산 → 상담사가 직접 통합 불가

2.2 구조적 한계

기존 ML 파이프라인 자체의 성능은 검증되어 있으나, 추천 결과가 상담사의 실제 콜에서 활용되지 못하는 구조적 문제가 존재합니다. 이는 기술적 결함이 아닌 정보 전달 방식의 한계입니다.

  • 추천 결과에 고객 맥락 없음 — 상품명만 있을 뿐, 이 고객에게 왜 이 상품인지 설명 부재. 상담사가 콜 전에 활용하지 않음
  • 캠페인 대상 추출 수작업 의존 — 기획 담당자가 직접 SQL을 작성하거나 개발팀에 요청해야 하는 비효율 발생
  • 녹취 데이터 미활용 — 약 5,000건의 녹취 데이터가 고능률 상담사의 성공 패턴을 담고 있음에도, 구조화되지 않아 조직 차원의 인사이트로 전환되지 못하고 방치
  • 분산된 데이터 소스 — 계약이력, 담보현황, 통화이력, 설계이력이 별개 시스템에 존재하여 상담사가 콜 전 통합 파악 불가
💡
본 프로젝트는 레거시 ML 배치를 대체하지 않습니다. 기존 AutoGluon 추천 결과를 INPUT으로 활용하면서, 그 위에 AI Agent 레이어를 얹어 상담사가 실제로 사용할 수 있는 형태로 변환하는 것이 핵심 목표입니다.
Section 3

솔루션 설계

3.1 전체 아키텍처

멀티모달 데이터 소스 4종을 전처리 파이프라인 3종으로 가공하고, LangGraph 기반 AI 에이전트가 이를 통합하여 Gradio UI 2탭으로 서비스합니다. 상담사(Tab1)와 기획자(Tab2)는 동일한 에이전트 백엔드를 서로 다른 인터페이스로 활용합니다.

Figure 1. 시스템 전체 데이터 흐름
데이터 소스 규모 전처리 파이프라인 저장소
Oracle DB (전사 고객, 계약/통화/캠페인이력) ~30만 명 Pipeline C (매일 cron) DuckDB 10개 테이블

3.2 데이터 파이프라인 3종

Pipeline A — STT 인덱싱 (1회성, resume 지원)

WAV 파일명(CALL_ID.wav)에서 Path.stem으로 CALL_ID를 파싱하여 DuckDB tbl_call_detail과 1-hop JOIN으로 고객번호(CTMNO) 및 메타데이터를 획득합니다. 이후 faster-whisper large-v3로 STT 수행 후, 개인정보 마스킹과 감성/요약 분석을 Qwen3.6 단일 호출로 통합 처리합니다.

입력WAV (CALL_ID.wav)
→
STTfaster-whisper
→
마스킹+분석Qwen3.6 (JSON)
→
임베딩nomic-embed-text
→
저장Chroma calls

Chroma에 저장되는 임베딩 텍스트(embedded_text)는 RAG 검색의 쿼리 텍스트와 동일한 의미 공간을 형성하도록 고객 프로필 + 요약 포맷으로 구성됩니다. 

# embedded_text 포맷 (Pipeline A 생성 시)
f"[고객: {age}세 {sex}, {campaign_nm}] {summary}"

# campaign_nm이 None인 경우 fallback
campaign_nm = campaign_nm or "캠페인미확인"

Pipeline B — 문서 인덱싱 (1회성, resume 지원)

상품설명서, 교육자료 등 내부 문서를 파싱하여 상품 정보 RAG의 기반을 마련합니다. 파일 형식별 전용 파서를 통해 마크다운으로 변환 후 임베딩합니다.

  • PDF → pymupdf4llm → 마크다운 (표 구조 보존)
  • DOCX → mammoth → 마크다운
  • PPTX → python-pptx → 슬라이드별 마크다운
  • 이미지 포함 문서 → Vision LLM(Qwen3.6 언로드 후 순차 실행) → 마크다운 변환

Pipeline C — DuckDB 마트 갱신 (매일 cron)

Oracle AI_* 추출 테이블에서 DuckDB 도메인 테이블로 매일 갱신합니다. 갱신 중 에이전트 쿼리 블로킹을 방지하기 위해 별도 파일(mart_new.db)에 전체 재적재 후 atomic rename으로 교체하는 방식을 사용합니다.

Section 4

AI Agent 핵심 기술

4.1 자율성 제어 철학

에이전트가 모든 것을 자율적으로 결정하는 방식이 아닌, 결정론적 워크플로(데이터 수집·분류)와 AI 자율성(스크립트 생성)을 명확히 분리하는 설계 철학을 택했습니다. 고객 분류(3분기)와 DB 조회는 결정론적으로 처리하여 정확성을 보장하고, 스크립트 생성 단계에서만 LangGraph CoT 에이전트의 자율성을 부여합니다.

4.2 LangGraph StateGraph — 8노드 파이프라인

Tab1 에이전트는 Tab1State TypedDict와 8개 노드로 구성된 StateGraph로 구현됩니다. checkpoint 없이 매 요청마다 fresh 그래프를 실행하며, tab1_handler.py가 스트리밍 래퍼 역할만 담당합니다.

Node 1
classify
3분기 자동 분류 (신규/미연결/이력)
Node 2
fetch_data
DuckDB 멀티 테이블 병렬 조회
Node 3
format_db
DB 결과 즉시 표시용 포맷 변환
Node 4
hyde
HyDE 가상 요약 생성 (RAG 품질 향상)
Node 5

Chroma 3단계 폴백 검색
Node 6
analyze
CoT 분석 + ReAct Lite 판단 (JSON)
Node 7*

Node 8

* Node 7은 analyze 노드의 판단에 따라 조건부 실행. 하이라이트 노드가 핵심 AI 처리 단계.

# agent/graph.py — StateGraph 플로우
classify
  → fetch_data
  → format_db          # ①DB 결과 즉시 Gradio 표시
  → hyde               # HyDE 가상 요약 생성
  → rag                # 성공 콜 + 상품문서 RAG
  → analyze            # CoT + ReAct Lite
  → [fetch_extra_products]  # 조건부
  → prepare_prompt
  → LLM 스트리밍        # ②스크립트 생성

4.3 HyDE — Hypothetical Document Embedding

고객 프로필 텍스트("52세 남성, 뇌혈관 담보 부재")와 과거 성공 콜 요약("[고객: 54세 남, TM캠페인A] 갱신 이력 언급 후 체결") 사이의 언어 공간 미스매치 문제를 해결하기 위해 HyDE 기법을 적용합니다.

검색 전 LLM이 먼저 "이 고객에게 맞는 가상의 성공 통화 요약"을 생성하고, 그 가상 요약 텍스트로 Chroma를 검색합니다. 실제 성공 콜 요약과 동일한 의미 공간에서 검색이 이루어지므로 관련성 높은 케이스를 찾을 수 있습니다. LLM 호출 실패 시 기본 프로필 텍스트로 폴백합니다.

4.4 Dynamic Few-Shot + In-Context Learning

RAG로 검색된 성공 콜 케이스의 실제 마스킹 원문(MASKED_TEXT)을 Few-Shot 예시로 prepare_prompt_node에서 프롬프트에 주입합니다. 파인튜닝 없이도 고능률 상담사의 어투·접근 방식을 LLM이 즉석에서 재현하는 In-Context Learning 효과를 얻습니다.

성공 콜 검색에는 3단계 폴백 전략을 적용하여 항상 유용한 케이스를 확보합니다.

  • 1순위 — 연결성공 + 우호적 고객 콜
  • 2순위 — 연결성공 콜 (감성 무관)
  • 3순위 — 필터 없음 (최소한의 컨텍스트라도 확보)

Chroma 결과가 없더라도 DuckDB + products RAG로 스크립트 생성은 정상 동작합니다.

4.5 ReAct Lite — 필요한 곳에만 자율성 부여

전체 파이프라인을 LLM이 주도하는 풀 ReAct 에이전트가 아닌, analyze_node에서만 제한된 자율성을 부여하는 방식입니다. LLM이 고객 분석 후 needs_product_search: bool을 판단하고, True이면 fetch_extra_products_node가 조건부로 실행됩니다. 이를 통해 불필요한 도구 호출을 최소화하고 파이프라인의 예측 가능성을 유지합니다.

4.6 CoT 2단계 체인

단일 LLM 호출로 스크립트를 직접 생성하는 방식 대신, 분석과 생성을 2단계로 분리합니다.

  • analyze_node — 고객 분석 JSON 출력: approach_angle (접근 각도) / key_points (핵심 포인트) / insight (인사이트) / needs_product_search
  • prepare_prompt_node + LLM 스트리밍 — 분석결과 + Few-Shot + 담보 커버리지 + 상품문서를 통합하여 최종 스크립트 생성

중간 분석 결과가 명시적으로 문서화되므로 LLM의 추론 품질이 향상되며, 동시에 스크립트 생성 근거를 추적하기도 용이합니다.

4.7 고능률 상담사 접근 키워드 (해시태그)

스크립트 하단에 성공 콜 케이스에서 추출한 핵심 접근 키워드를 해시태그 형식으로 자동 생성하여, 상담사가 이번 콜의 전략적 포인트를 한눈에 파악할 수 있게 합니다.

4.8 캠페인 타겟 추출 3전략 (Tab2)

기획 담당자의 목적에 따라 3가지 추출 전략 중 선택합니다. 모든 조건은 폼 Q&A를 통해 구조화된 conditions dict로 변환되고, build_campaign_query() 템플릿 함수가 DuckDB 쿼리를 생성합니다. LLM이 SQL을 직접 생성하지 않아 안정성과 예측 가능성을 확보합니다.

전략 1
과거 실적 기반
캠페인 배정일 기준 +90일 이내 계약 체결(성공 기준)된 고객 세그먼트의 조건을 재현하여 동일 패턴의 타겟을 추출. 과거 이력이 없는 신규 캠페인에서는 비활성화.
전략 2
활성도 기반
최근 6개월 내 연결성공 또는 캠페인 배정이력이 있는 고객 필터 + Step 0 조건(상품/채널/성별/연령) 교차 필터. ML 점수 테이블 불필요 — DuckDB 집계로 직접 산출.
전략 3
룰베이스
담당자가 직접 조건을 설정하는 방식. AI가 전부 결정하는 것이 아닌, 담당자 판단과 AI 추천이 함께 작동하는 구조를 지향.
ℹ
예상 성과 산출 방식 — ML 예측 모델이 아닌 과거 유사 캠페인의 실제 체결율을 DuckDB로 집계한 참고치를 제공합니다. UI에 "ML 예측 아님, 과거 실적 참고치" 문구를 명시하여 투명성을 확보합니다.

6.1 폐쇄망 배포 전략

서비스 서버는 인터넷이 완전 차단된 폐쇄망(Ubuntu x64, Python 3.10, CUDA 12.4, GPU 40GB)에 위치합니다. 오픈망 PC(Windows, 관리자 권한 없음)에서 망간 파일 전송 시스템을 경유하여 반입하는 방식을 사용합니다.

  • 번들 패키지 — Colab 스크립트(colab_bundle_download.py)로 의존성 패키지를 tar.gz 형식으로 다운로드. 개별 파일 2GB 초과 시 분할, 각 파트 확장자 반드시 .tar.gz
  • LLM 모델 — colab_model_download.py로 Qwen3.6-27B Q4_K_M GGUF 다운로드 + 분할. Ollama GGUF 직접 임포트로 별도 변환 불필요
  • Ollama 바이너리 — ollama-linux-amd64.tar.zst (v0.24.0+) 단일 바이너리 반입, CUDA 자동 감지
  • LangChain Hub / LangSmith 의존성 제거 — 폐쇄망 HTTP 통신 불가, RAG 프롬프트는 한국어 도메인 맞춤으로 직접 작성

📞
상담사 관점
콜 전 고객 파악에 여러 시스템을 번갈아 조회해야 했던 방식에서, 고객번호 하나로 계약현황·보장현황·스크립트를 즉시 조회하는 방식으로 전환됩니다. 더 중요한 점은 고능률 상담사의 노하우가 전체 상담사에게 확산된다는 것입니다. 성공 콜 녹취 패턴이 Few-Shot으로 주입되어, 경력에 무관하게 수준 높은 접근 방식의 스크립트를 활용할 수 있습니다.
📊
기획자/운영자 관점
캠페인 대상 추출을 위해 수작업 SQL을 작성하거나 개발팀에 요청하던 방식에서, 대화형 폼 Q&A로 직접 추출하는 방식으로 전환됩니다. 과거실적 기반·활성도 기반·룰베이스 3가지 전략을 목적에 따라 선택할 수 있어, 캠페인 성격에 맞는 타겟 리스트를 독립적으로 생성할 수 있습니다.
🔗
레거시 연동 확장
Gradio API를 통해 이노스(장기TM 상담사 화면)의 상품추천란에 스크립트를 직접 적재할 수 있는 구조로 준비되어 있습니다. 기존 레거시 화면 수정 없이 AI 추천 결과를 주입하는 방식으로 점진적 확장이 가능합니다.
🗄
캠페인 배정 원스톱
현재 Excel(CTMNO) 다운로드 방식에서, DuckDB 타겟 리스트 테이블 직접 생성 → 전사DB통합관리시스템 연동 → 캠페인 배정까지 원스톱으로 연결되는 구조로의 확장이 예정되어 있습니다.
💡
레거시 ML 배치와의 공존 — 본 시스템은 AutoGluon 기반 상품추천 배치를 대체하지 않습니다. 레거시 ML 결과를 tbl_recommendation으로 적재하여 Agent의 INPUT으로 활용하는 구조이며, "이미 운영 중인 ML 위에 AI Agent를 얹어 상담사가 실제로 사용할 수 있는 형태로 변환"하는 것이 프로젝트의 핵심 포지셔닝입니다.
