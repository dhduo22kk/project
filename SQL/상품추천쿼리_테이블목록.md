## 중복 정보 분석

### ① GD_TYPE CASE WHEN 로직 — 4곳에서 동일 블록 반복

동일한 20줄짜리 CASE WHEN이 아래 테이블에서 각각 직접 작성됨.

| 위치 | 테이블 | 비고 |
|------|--------|------|
| line 8 | `GDREC_TMGD_LIST` | TM 상품 한정 |
| line 896 | `GDREC_ORIGIN_INS_GD_PRED` | INS_CR_PRED 기반 |
| line 982 | `GDREC_ORIGIN_INS_ADDGD_PRED` | ADDCR_PRED 기반 |
| line 1411 | `GDREC_ORIGIN_INS_PRVGD_PRED` | 해지 이력 |

→ `GDREC_TMGD_LIST`에서 한번만 정의하고 GDCD 기준 JOIN으로 재사용하면 제거 가능.  
→ 단, `GDREC_TMGD_LIST`는 TM 판매중 상품만 포함 — 판매 중단 상품 GD_TYPE이 NULL이 될 수 있어 전채널/이력 조회 시 누락 위험 있음.

### ② 계약자 / 피보험자 연령·성별 — 거의 동일한 쿼리 2개

| 테이블 | 대상 키 | CUS_CTM JOIN 조건 |
|--------|---------|-------------------|
| `GDREC_ORIGIN_INS_CRTINFO_PRED` | CRT_CTMNO (계약자) | B.CTMNO = A.CRT_CTMNO |
| `GDREC_ORIGIN_INS_NRDINFO_PRED` | MN_NRDPS_CTMNO (피보험자) | B.CTMNO = A.MN_NRDPS_CTMNO |

계산 로직(F_BIRTH_DAY_DEC → MONTHS_BETWEEN → 연령, F_SEX_DEC → 성별)이 완전히 동일.  
대상 고객번호만 다름. UNION ALL 또는 단일 쿼리에 두 키를 UNPIVOT해서 CUS_CTM 1회 스캔으로 처리 가능.

### ③ M_BIZ_RECT_GDINFO_L* — 5개 테이블이 동일 구조

| 테이블 | GD_TYPE 필터 | PERCENTILE_CONT 대상 담보 |
|--------|-------------|--------------------------|
| `M_BIZ_RECT_GDINFO_L01` | L01, 유병자, L04 | 뇌혈관/심장/암/질병사망 |
| `M_BIZ_RECT_GDINFO_L03` | L03 | 대인합의/변호사/운전자벌금/자동차부상 |
| `M_BIZ_RECT_GDINFO_SS` | SS | 질병/상해 입원·통원 실손 |
| `M_BIZ_RECT_GDINFO_L08` | L08 | 중증치매/장기요양 |
| `M_BIZ_RECT_GDINFO_L11` | L11 | 화재벌금/일상배상/자동차부상 |

쿼리 골격(GDREC_ORIGIN_INS_CR_PRED × M_CRM_REC_GDNM_TM × T09 + PERCENTILE_CONT + AGE_SEG)이 동일.  
GD_TYPE 필터와 PERCENTILE_CONT 대상 컬럼만 다름.  
→ 하나의 쿼리에 GD_TYPE 컬럼 포함해서 GROUP BY에 추가하면 통합 가능.

### ④ INS_GD_PRED vs ADDGD_PRED — 동일 PIVOT 구조, 소스만 다름

| 테이블 | 소스 | 의미 |
|--------|------|------|
| `GDREC_ORIGIN_INS_GD_PRED` | GDREC_ORIGIN_INS_CR_PRED | 현재 보유 계약의 상품유형별 계약수 |
| `GDREC_ORIGIN_INS_ADDGD_PRED` | GDREC_ORIGIN_INS_ADDCR_PRED | 추가 계약의 상품유형별 계약수 |

PIVOT 컬럼 구성(L01/L03/L04/.../L123) 동일.  
→ 소스 테이블 UNION 후 FLAG 컬럼(본계약/추가계약) 추가하거나, 별도 유지 시 PIVOT 코드만 공통화 가능.

### ⑤ CLM_CSF / CLM_MTT / CLM_HSP — 청구 vs 고지 정보 구분 필요

| 테이블 | 내용 | 소스 테이블 |
|--------|------|------------|
| `GDREC_ORIGIN_CLM_CSF_PRED` | 중대질환 **청구** (실제 보험금 지급) | M_CMP_GN_CVRCL_PY 계열 |
| `GDREC_ORIGIN_CLM_MTT_PRED` | 중대질환 **고지** (계약 시 고지 이력) | INS_CR_MTT 계열 |
| `GDREC_ORIGIN_CLM_HSP_PRED` | 입원/수술 **고지** | INS_CR_MTT 계열 |

성격이 다르므로(청구 vs 고지) 통합 불가. 단, MTT/HSP는 동일 소스(INS_CR_MTT)에서 질환 필터만 다름 → 하나의 쿼리로 합칠 수 있음.

### ⑥ MAIN99 vs MAIN9 — 단계 구분

| 테이블 | 포함 정보 | 없는 정보 |
|--------|----------|----------|
| `GDREC_ORIGIN_MAIN99_PRED` | 계약수/보험료/피보험자/자동차/직업/청구/부담보/연령성별 | 담보금액(T09), 설계 이력, 추가계약, 채널별 기가입 |
| `GDREC_ORIGIN_MAIN9_PRED` | MAIN99 전체 + T09 담보금액 + GD_PRED + CHNL_PRED + ADDGD + 설계 | 청구 정보 |
| `GDREC_ORIGIN_MAIN_FIN_PRED` | MAIN9 + 청구 정보 + 최종 추천 필터 | — (최종) |

→ 두 단계 취합이 필요한 이유: T09 담보금액 계산(T02→T09)이 MAIN99보다 나중에 끝남.  
→ 구조 자체는 정상. 중복이 아니라 의존성에 의한 순차 생성.
